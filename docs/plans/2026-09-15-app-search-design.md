# App 搜索功能设计文档

日期：2026-09-15
状态：已确认，进入实施计划阶段

## 一、要解决的问题

主列表是全量的：本机实测 122 个应用全在 `updates` 里，不是只有可更新的那 22 个。三档分组把人按「该不该动手」分好了，但要找**某一个**应用时，只能拿眼睛在几十行里扫。

这个需求在升级收尾时最尖锐：界面提示某个应用升完了，用户想知道它现在是什么状态，却得从头翻一遍。

因此要加的是一个**过滤器**，不是一个检索引擎——数据早就在手里，缺的只是「把其余的行收起来」。

## 二、范围

### 做

1. 主窗口 header 加一个搜索框，输入即实时过滤三档分组里的条目。
2. 匹配 `app.name` 与 `app.bundleID`，不区分大小写，多词按空白切分、全部命中才通过。
3. 搜索激活时显示命中数与总数（`命中 3 / 共 122`）。
4. 「全部升级」收窄为「只升筛出来的」，文案随之变（`升级这 3 个`）。
5. 筛选零命中时给一个**区别于「尚未检查」**的空态，带「清除筛选」出口。
6. `⌘F` 聚焦搜索框，`Esc` 清空。
7. 截图通道加 `--query`，让筛选态能留痕、能重跑。

### 不做

- 模糊 / 子序列匹配（`chrstd` → Cherry Studio）、拼音首字母
- 搜索历史、搜索建议、匹配片段高亮
- 搜版本号、路径、来源徽标
- `⌘K` 命令面板、独立搜索结果页
- 菜单栏下拉里搜索
- 搜索词持久化（窗口重开即清空）

**这个功能的边界：只改变「哪些行显示出来」，不改变任何检查结果、不发起任何请求、不写入任何东西。**

## 三、关键决策

### 3.1 形态：过滤现有列表，不做命令面板

扫描结果本来就是全量的，列表已经在手边，加一个过滤器的边际成本接近于零。命令面板要多做一层浮层 UI、键盘导航与动作路由，收益只是「少点一次方向键」。独立结果页则要在主列表外再维护一套行渲染，两边的按钮态与升职中状态得长期保持同步——这是最容易悄悄腐烂的那类重复。

### 3.2 匹配字段：名称 + Bundle ID

只搜名称实现最小，但搜 `com.tencent` 这类要一次定位一族应用时就废了，而 Bundle ID 就在 `AppInfo` 里躺着，成本只是多一个字段。**不搜路径**：`/Applications/` 是全部条目共有的前缀，搜它必然全量命中，噪声大于价值。

### 3.3 双口径：统计卡片读全量，列表与批量按钮读筛选

这是本设计里唯一容易做错的地方。

三张统计卡片（可更新 / 已是最新 / 无法自动检测）回答的是「**这台机器整体什么样**」。跟着筛选词跳会让人以为机器变了；而且菜单栏徽标取的是同一个 `updateCount`（`AppUpdaterApp.menuLabel`），两个口径会当场打架——图标旁边写着 22，卡片写着 3。

所以：

| 界面元素 | 数据来源 |
|---|---|
| 三张统计卡片 | `store.updates`（全量，纹丝不动） |
| 分组列表 | 筛选结果 |
| 「全部升级」按钮 | 筛选结果 |

筛选激活时，header 副标题改口径承担告知义务：`筛选 “ch stu” · 命中 3 / 共 122`。

### 3.4 匹配逻辑做成独立纯函数

新增 `Sources/AppUpdaterKit/Models/AppSearch.swift`，**不放进 `UpdateStore`，也不放进视图**。

理由是跟着 `CheckScheduler` 已经走通的那条路：`CheckPlanner`（Core）只回答「现在该不该查」，`UpdateWatcher`（UI）只管计时与唤醒监听。搜索同理——`AppSearch` 只回答「这条记录匹不匹配」，视图只管渲染。好处是这批边界断言（空词、纯空白、大小写、多词、nil Bundle ID、中文名）不需要 GUI、不需要真机，能密集地写。

**也不把它做成 `UpdateStore` 的一个 `@Published var query`**：搜索是瞬时的视图态，不该进状态源。`UpdateStore` 已被 170+ 个测试覆盖，加一个纯 UI 字段只会扩大它的职责面。因此筛选词用 `ContentView` 的 `@State` 持有，视图把过滤结果**作为参数**传给 store 的批量升级入口——store 始终不知道「搜索」这件事存在。

### 3.5 自绘搜索框，不用 `.searchable`

`.searchable` 能白拿 `⌘F` 与系统观感，但它的落点依赖 `NavigationStack` / `toolbar` 容器，而主窗口是一段自排的 `VStack`，搜索框会被塞到哪一层不可预期。而且 `--snapshot` 通道要求渲染确定、可复现——系统接管布局的控件在离屏渲染里是个变量。

代价是 `⌘F` 要自己接。

## 四、匹配规则

```swift
public enum AppSearch {
    /// "  ch   stu  " → ["ch", "stu"]；空数组表示「不筛选」
    public static func tokenize(_ query: String) -> [String]
    public static func matches(_ update: AppUpdate, tokens: [String]) -> Bool
    public static func filter(_ updates: [AppUpdate], query: String) -> [AppUpdate]
}
```

| 规则 | 说明 |
|---|---|
| 归一化 | 按空白切分。切分为空数组 = **不筛选**，原样返回全量（不是返回空——这是最容易写反的一处） |
| 字段 | `app.name`、`app.bundleID`；`bundleID == nil` 时跳过（纯命令行 cask 就是这种） |
| 谓词 | `localizedCaseInsensitiveContains`，中文名（微信）自然命中 |
| 多词 | 每个 token 都要在「name 或 bundleID」里命中（AND）。`"ch stu"` 与 `"stu ch"` 等价 |
| 跨字段 | 允许 token 分别命中不同字段：`"cherry com.kangfenmao"` 成立 |
| 顺序 | 过滤不改顺序，沿用 `AppUpdate.listOrder` 排好的结果 |

## 五、界面与交互

```
┌─────────────────────────────────────────────────────────────┐
│ App 更新                            [🔍 搜索] [全部升级] [重新检查] [⚙] │
│ 筛选 “ch stu” · 命中 3 / 共 122                                │
├─────────────────────────────────────────────────────────────┤
│ [可更新 22]  [已是最新 74]  [无法自动检测 26]   ← 全量口径，不跳    │
├─────────────────────────────────────────────────────────────┤
│ 可更新                                              1        │
│   ● Cherry Studio   Sparkle · 1.8.4 → 2.0.9 · 372 MB  [升级] │
└─────────────────────────────────────────────────────────────┘
```

- 搜索框进现有 header，紧跟在 `Spacer` 之后（放大镜 + 内建清除按钮）
- 分组保留、空分组自动隐藏——现有代码的 `if !items.isEmpty` 已天然满足，不用改
- 批量按钮：`item.isAutomated` 计数 `> 1` 才出现（沿用现有规则），文案 `升级这 N 个`
- `⌘F` 聚焦：视图内挂一个零尺寸的隐藏按钮接快捷键（不污染菜单栏，也不需要跨层通信）
- `Esc` 清空：`.onExitCommand { query = "" }`

## 六、边界与空态

| 情况 | 行为 |
|---|---|
| 筛选零命中 | 新增空态：「没有匹配 "x" 的应用」+「清除筛选」按钮 |
| 与「尚未检查」空态 | **两套文案必须不同**。现有空态只在 `store.updates.isEmpty` 触发，用户分不清「没搜到」和「没查过」是硬伤 |
| 检查进行中带查询词 | 结果回来重新过滤，`AppSearch.filter` 是派生计算，天然满足 |
| 升级完一条后它不再匹配 | 不会发生——匹配只看 `name` / `bundleID`，升级不改这两个字段 |
| 搜索词含引号 / 特殊字符 | 纯子串比较，无正则、无转义，不存在注入面 |
| 窗口重开 | 搜索词清空（`@State` 不持久化） |

## 七、测试策略

**分层**：匹配规则是纯逻辑，用密集单测守住；界面行为靠截图与真机。

`Tests/AppUpdaterTests/AppSearchTests.swift`：

- 空词、纯空白词 → 返回全量（**不是**返回空）
- 首尾空白被裁掉：`"  iina  "` 命中
- 大小写不敏感：`CHERRY` 命中 `Cherry Studio`
- Bundle ID 命中：`com.colliderli` 命中 IINA
- `bundleID == nil` 不崩
- 多词 AND 正反例：`ch stu` 命中、`ch zzz` 不命中
- 跨字段：`cherry com.kangfenmao` 成立
- 零命中 → 空数组
- 中文名命中
- 顺序保持：过滤后仍等于输入顺序的子序列

`Tests/AppUpdaterTests/UpgradeTests.swift` 补一条：

- `UpdateStore.automatedCandidates(in:)` 只返回传进来的那批里可自动完成的条目——守住「批量升级不顺手升全量」这条边界

**截图通道**：新增 `--query <词>`，作用于 `main` 模式。给 `ContentView` 加 `initialQuery` 注入点（默认 `""`），生产路径不受影响。

**真机验证（单元测试覆盖不到的部分）**：

- `⌘F` 聚焦、`Esc` 清空是否真的生效（SwiftUI 快捷键需要真窗口）
- 搜索框在 760pt 最小宽度下与「全部升级 / 重新检查」按钮是否挤在一起
- 筛选后点「升级这 N 个」，确认只有筛出来的条目进了任务面板

## 八、已知取舍

1. **多词 AND 有轻微误命中**：`mac mouse` 也会命中 「Mac Mouse Fix」，这是分词搜索的正常行为，不是 bug。
2. **不搜路径**意味着按安装目录找应用不行（如「Setapp 装的那些」）。真需要时再单独议，别提前加字段。
3. **`⌘F` 挂隐藏按钮**是 SwiftUI on macOS 的常规变通。若实测不生效，退路是改用 `AppUpdaterApp.commands` 里的 `CommandGroup` + `NotificationCenter` 转发——代价是多一层跨层通信。
4. **本机没有 Xcode**，`swift test` 跑不了（README 已记录这条限制）。因此纯逻辑的验证走 `swiftc` 直编一个断言驱动，仓库里的 XCTest 用例交给 CI（`macos-latest` 有完整 Xcode）。两条路都在，只是分工不同。
